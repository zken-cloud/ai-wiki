### [GLM-5.3 Optimizations, Part 2: PCP, DCP, and Hybrid HiSparse on 16 H200s](https://vllm.ai/blog/2026-10-23-glm53-part2-pcp-dcp-hisparse)

**vLLM Blog** · 2026-10-23

vLLM optimizes GLM-5.3 serving on 16 H200 GPUs using Parallel Context Parallelism (PCP) and Deepseek Context Parallelism (DCP) for prefill, alongside Hybrid HiSparse for decode, enabling 1M-token contexts.

- PCP splits prefill prompts into 16 balanced chunks across 8 prefill GPUs using a front-and-back pairing pattern to distribute causal attention load equally.
- Combining PCP with DCP removes KV cache replication across ranks, scaling sparse Multi-head Latent Attention (MLA) efficiency from 26 to 191 FLOPs per byte moved.
- PCP prevents quadratic growth of the attention indexer by sharding tokens, pushing the point where indexer FLOPs exceed sparse MLA FLOPs from 32K tokens (under TP8) to 256K tokens.
- The deployment disaggregates prefill and decode across two 8x H200 nodes using vLLM's modular Model Runner V2 architecture.

**Why it matters:** This architectural combination eliminates memory and prefill bottlenecks for ultra-long context agentic workloads, boosting throughput and enabling execution of million-token prompts.

### [Orchestrating SageMaker AI endpoint auto scaling with AWS CDK](https://aws.amazon.com/blogs/machine-learning/orchestrating-sagemaker-ai-endpoint-auto-scaling-with-aws-cdk/)

**AWS Machine Learning Blog** · 2026-10-23

A reusable AWS CDK construct uses custom resources and explicit dependency ordering to automatically deregister and register Application Auto Scaling around SageMaker AI real-time endpoint updates.

- Native CloudFormation deployments fail during endpoint updates because SageMaker AI rejects changes while variants remain registered as scalable targets.
- Manual deregistration causes silent failures where auto scaling is omitted, or stack failures (UPDATE_ROLLBACK_FAILED) when auto scaling parameters change.
- The construct replaces native ScalableTarget and ScalingPolicy resources with three custom resources executed in sequence.
- The orchestration sequence handles deregistration, executes the CDK endpoint update, registers the scalable target once InService, and applies the target tracking policy.
- Asynchronous completion patterns in the CDK provider framework manage waiting for the endpoint and scalable target readiness.

**Why it matters:** This pattern eliminates manual CLI interventions and stack rollbacks, enabling zero-downtime SageMaker endpoint updates and auto-scaling reconfigurations within a single automated deployment pipeline.

### [Multi-Turn Reinforcement Learning on Amazon SageMaker AI: A hands-on guide](https://aws.amazon.com/blogs/machine-learning/multi-turn-reinforcement-learning-on-amazon-sagemaker-ai-a-hands-on-guide/)

**AWS Machine Learning Blog** · 2026-10-23

AWS has introduced a hands-on guide for training models on multi-turn agentic workflows using Multi-Turn Reinforcement Learning (MTRL) on Amazon SageMaker AI and Amazon Bedrock AgentCore.

- Uses Group Relative Policy Optimization (GRPO) to update a Low-Rank Adaptation (LoRA) adapter based on the spread of rewards across rollouts.
- Decouples infrastructure by housing the policy model in SageMaker AI while running the agent environment, tools, and outcome-based reward logic inside AgentCore.
- Demonstrates MTRL on gpt-oss-20b playing Wordle, which improved solve rates from 61% to 84% at default reasoning effort and 15% to 69% at low reasoning effort for ~$339 in training tokens.
- Requires only the initial task state (e.g., secret word) in the training dataset, relying on an outcome-dominant reward function (1.05-1.55 for solves, -0.5 for losses).

**Why it matters:** MTRL enables enterprises to fine-tune small, cost-effective models for complex multi-step business workflows where step-by-step labeled trajectories do not exist and feedback is only available at sequence completion.

### [Reduce ASR inference costs by 75% with NVIDIA MPS on Amazon EC2](https://aws.amazon.com/blogs/machine-learning/reduce-asr-inference-costs-by-75-with-nvidia-mps-on-amazon-ec2/)

**AWS Machine Learning Blog** · 2026-08-27

AWS, NVIDIA, and Heidi Health demonstrated using NVIDIA CUDA Multi-Process Service (MPS) with Triton Inference Server on Amazon EC2 to reduce GPU infrastructure requirements for ASR inference by 75 percent while maintaining sub-second latency.

- Single ASR inference requests for the Parakeet TDT 0.6B V2 model utilize only 15–20% of an NVIDIA L40S GPU's 142 streaming multiprocessors (SMs), leaving ~80% idle under default CUDA time-slicing.
- CUDA MPS routes work through a single daemon-managed context, enabling concurrent kernel execution across shared SMs without context-switching overhead or code changes.
- Deploying MPS reduced Heidi Health's required Amazon EC2 GPU instances from 16 to 4 while sustaining 92.1 requests per second (RPS) per GPU under sub-second latency SLAs (mean < 650 ms, p99 < 1,000 ms).

**Why it matters:** Utilizing CUDA MPS enables organizations to dramatically lower cloud GPU infrastructure costs for low-utilization ASR workloads without violating strict real-time latency SLAs.

### [NVIDIA NVLink Fusion Expands With NVHBM Custom High-Bandwidth Memory](https://blogs.nvidia.com/blog/nvlink-fusion-nvhbm-custom-high-bandwidth-memory/)

**NVIDIA Blog** · 2026-08-26

NVIDIA expanded NVLink Fusion by introducing NVHBM, a custom high-bandwidth memory architecture that integrates the memory controller directly into the 3D HBM base die instead of the XPU compute die.

- NVHBM moves the memory controller to the 3D HBM stack, freeing up to 25% more silicon area on the XPU compute die compared to standard HBM4E.
- The new memory technology delivers up to 30% greater memory bandwidth and reduces HBM power consumption by 15%.
- Amazon's Annapurna Labs is the first collaborator adopting NVHBM and will support NVLink Fusion starting with its Trainium4 chips.
- NVIDIA is establishing a standardized NVHBM implementation that will be validated and supplied by multiple memory partners.

**Why it matters:** By decoupling the memory controller from the compute die and standardizing the interface, hyperscalers can build semi-custom XPUs with higher compute density and improved energy efficiency.

### [Evaluate any agent framework with Amazon Bedrock AgentCore Evaluations](https://aws.amazon.com/blogs/machine-learning/evaluate-any-agent-framework-with-amazon-bedrock-agentcore-evaluations/)

**AWS Machine Learning Blog** · 2026-08-26

Amazon Bedrock AgentCore evaluations uses OpenTelemetry standards to evaluate AI agents across diverse frameworks like LangGraph, LlamaIndex, and OpenAI Agents SDK without needing framework-specific SDK integration.

- Decouples agent evaluation from specific SDKs by consuming standard OpenTelemetry traces collected via the AWS Distro for OpenTelemetry (ADOT) and Amazon CloudWatch.
- Filters full execution traces down to three core span roles required for evaluation: invoke agent (top-level request/response), inference (model calls and message history), and execute tool (tool inputs/outputs).
- Supports both OpenTelemetry GenAI semantic conventions (such as chat, retrieval, and execute_tool) and OpenInference span kinds (such as LLM, TOOL, RETRIEVER, and CHAIN).
- Ignores non-essential spans like retrieval, reranking, guardrails, and memory without requiring special configuration or breaking evaluation pipelines.

**Why it matters:** Engineers can evaluate agent performance across multiple disparate frameworks using a single standardized telemetry-based evaluation pipeline on Amazon Bedrock AgentCore runtime.

**AWS Machine Learning Blog** · 2026-08-26

AWS outlines advanced data optimization strategies for supervised fine-tuning, focusing on empirical dataset size evaluation using learning curve analysis.

- Typical SFT baseline requirements range from 500 samples for simple style changes to over 10,000 samples for complex multi-step reasoning tasks.
- Learning curve analysis can be conducted in a single training run by evaluating intermediate checkpoints saved every 10–20 percent of training against a held-out benchmark.
- Data scaling saturation is reached when doubling the training data yields less than a 1–2 percent improvement on the primary downstream metric.

### [Preparing data for supervised fine-tuning Part 1: Formatting and quality](https://aws.amazon.com/blogs/machine-learning/preparing-data-for-supervised-fine-tuning-part-1-formatting-and-quality/)

**AWS Machine Learning Blog** · 2026-08-26

Part one of this series details foundational data preparation methods for supervised fine-tuning (SFT), emphasizing that high data quality, strict accuracy, and semantic diversity outperform sheer dataset size.

- Post-training customization uses three sequential levers: Continued Pre-training (CPT) to expand knowledge, SFT to shape output behavior and schema adherence, and Reinforcement Fine-Tuning (RFT) to optimize via reward signals.
- Data quality takes precedence over volume; research shows 1,000 highly curated examples (LIMA) or filtering to the top 20% cleanest examples (AlpaGasus) achieves higher performance than larger, noisy datasets.
- Generalization during SFT depends heavily on dataset diversity, specifically semantic coverage (breadth of task domains and prompt phrasings) and information depth (richness of individual examples).

**Why it matters:** Prioritizing strict quality checks and semantic diversity over large data quantities reduces compute costs and prevents models from learning persistent incorrect response patterns.

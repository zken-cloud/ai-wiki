### [Following the Bottleneck: Optimizing MiniMax M3 on AMD Instinct MI355X](https://vllm.ai/blog/2026-09-10-minimax-m3-mi355x)

**vLLM Blog** · 2026-09-10

Engineers optimized MiniMax M3 serving on AMD Instinct MI355X GPUs in vLLM by applying shape-aware kernel launchers and tile selection based on local execution dimensions.

- MiniMax M3 features 60 total decoder layers, with 57 utilizing sparse MoE and sparse attention.
- Tensor parallelism (TP8) shards query heads to 8 per rank while replicating KV and index heads (1 per rank), creating a local QKV projection dimension of N=1536.
- PR #45725 split kernel launchers into large-M (prefill) and small-M (decode) regimes, achieving a 7.8% to 9.4% output throughput improvement for TP8 at 8K input/1K output.
- PR #46117 optimized decoding using narrower N tiles to expose independent work and larger K steps to lower loop iterations.

**Why it matters:** Tailoring CUDA/HIP tile sizes and launchers to local tensor shapes significantly improves LLM decoding throughput on AMD Instinct hardware.

### [When to Use Encode-Prefill-Decode Disaggregation to Accelerate Multimodal Model Serving](https://developer.nvidia.com/blog/when-to-use-encode-prefill-decode-disaggregation-to-accelerate-multimodal-model-serving/)

**NVIDIA Developer Blog** · 2026-09-09

NVIDIA Dynamo introduces encode-prefill-decode (EPD) disaggregation to optimize multimodal inference, achieving up to 5x performance gains by separating the vision encoder, prefill, and decode stages.

- EPD disaggregation isolates the vision encoder stage from the LLM prefill and decode stages during multimodal model inference.
- The technique provides the largest performance gains for image-heavy input prompts with short-to-medium output lengths.
- EPD disaggregation is particularly effective when applied to quantized mixture-of-experts (MoE) models.

**Why it matters:** Disaggregating multimodal inference stages with NVIDIA Dynamo allows developers to optimize hardware utilization and significantly accelerate serving throughput for vision-language models.

### [Deploying Qwen3.8-2.4T-A95B on Amazon SageMaker HyperPod with vLLM](https://aws.amazon.com/blogs/machine-learning/deploying-qwen3-8-2-4t-a95b-on-amazon-sagemaker-hyperpod-with-vllm/)

**AWS Machine Learning Blog** · 2026-09-09

Alibaba released open weights for Qwen3.8-2.4T-A95B, a 2.4-trillion-parameter MoE model deployable on Amazon SageMaker HyperPod using vLLM and NVIDIA B300 GPUs.

- Features 2.4 trillion total parameters with 95 billion activated per token across 512 routed experts and 1 shared expert (10 routed activated per token).
- Uses a hybrid architecture with 69 Gated DeltaNet linear attention layers and 23 Gated Attention quadratic layers to bound memory up to a 1M extensible context window.
- Supports native Multi-Token Prediction (MTP) draft heads for speculative decoding without needing a separate draft model.
- NVFP4 and MXFP4 (W4A4) quantizations compress weights to ~1.2 TB, enabling deployment on a single 8x NVIDIA B300 Blackwell Ultra node (ml.p6-b300).
- Provides built-in reasoning controls via a reasoning_effort parameter ('low', 'medium', 'high') for dynamically trading compute for reasoning depth.

**Why it matters:** It allows organizations to run a frontier Qwen-Max-class model entirely within their own AWS infrastructure without per-token API fees or data exposure.

### [Simplify and support your TorchServe workloads using Ray Serve Deep Learning Containers](https://aws.amazon.com/blogs/machine-learning/simplify-and-support-your-torchserve-workloads-using-ray-serve-deep-learning-containers/)

**AWS Machine Learning Blog** · 2026-09-09

AWS has launched new Ray Serve Deep Learning Containers (DLCs) for Amazon EKS, EC2, and SageMaker to provide a pre-built, tested inference stack following the deprecation of TorchServe.

- TorchServe is no longer actively maintained, receiving no planned updates, bug fixes, or security patches.
- The GPU variant of the Ray Serve DLC uses the NVIDIA Amazon Linux 2023 base image, bundling CUDA runtime, PyTorch, Ray Serve, FastAPI, Uvicorn, and hardware-accelerated FFmpeg.
- Ray Serve eliminates TorchServe artifacts like custom handlers, torch-model-archiver steps, and config.properties files, replacing them with @serve.deployment decorated Python classes.
- Serving applications can be injected directly into the container using Kubernetes ConfigMaps without rebuilding the base image.

**Why it matters:** Engineers using TorchServe can migrate to an AWS-maintained, security-patched inference runtime without manually managing GPU, CUDA, and PyTorch dependency chains.

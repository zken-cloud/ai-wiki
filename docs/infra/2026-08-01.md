**vLLM Blog** · 2026-07-29

vLLM on Arm CPUs has been optimized through collaborations with PyTorch, oneDNN, and KleidiAI communities, resulting in improved usability, broader model support, and substantial performance gains.

- Initial benchmarks in October 2025 showed vLLM on Arm CPUs had lower-than-expected performance, with 80% of runtime in dense layers dispatched to BF16 GEMMs.
- Memory allocation was a bottleneck due to PyTorch's use of glibc malloc, leading to poor reuse of large allocations and high page faults.
- Mimalloc was enabled as the default allocator on Arm-based CPUs in PyTorch to address memory allocation issues, improving Llama 3.1 8B offline throughput by 2.3x and low-concurrency serving gains by 7x.
- Optimizations focused on allocator behavior, runtime synchronization, framework overheads, attention kernels, and quantized execution, rather than just GEMM kernels.

**Why it matters:** These optimizations make vLLM more efficient and cost-effective for deploying large language models on Arm Neoverse-based servers, enhancing their utility in cloud and enterprise data centers.

### [Parallel All the Way Down: Beyond Single-Token Generation with Speculative Decoding](https://vllm.ai/blog/2026-07-28-speculators-parallel-drafting)

**vLLM Blog** · 2026-07-28

vLLM and Speculators now support P-EAGLE, DFlash, and DSpark, three parallel drafting algorithms that generate entire blocks of candidate tokens concurrently, moving beyond sequential token generation in speculative decoding.

- Traditional speculative decoding frameworks like EAGLE-3 use auto-regressive drafting, requiring a separate forward pass for each candidate token, introducing sequential latency.
- Parallel drafting algorithms predict an entire candidate block of tokens concurrently in a single forward pass, decoupling proposal generation latency from the number of tokens speculated.
- This architectural shift allows for larger, more expressive draft architectures without sequential latency penalties and simplifies parameter tuning by removing the dependency of drafting cost on block length.
- P-EAGLE, DFlash, and DSpark combine parallel execution with deep verifier-state conditioning, building on the insight from EAGLE to generate draft tokens.
- A shared challenge for parallel speculators is training, as they must perform next-K prediction at every token position along a training sequence.

**Why it matters:** This advancement significantly mitigates memory-bandwidth bottlenecks in LLM serving, leading to substantial inference speedups in production systems.

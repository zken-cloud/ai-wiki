### [Accelerating PyTorch on AMD GPUs with FlyDSL](https://pytorch.org/blog/accelerating-pytorch-on-amd-gpus-with-flydsl/)

**PyTorch Blog** · 2026-10-21

FlyDSL now integrates into PyTorch as an optional backend for AMD MI350-series GPUs, delivering lower-level hardware mapping control and performance gains across GEMM, attention, RMSNorm, and TopK operators.

- Uses Python-based layout algebra and MLIR to provide explicit kernel-level control over wave/thread mappings, MFMA atoms, LDS swizzling, and dual-wave software pipelining.
- Integrated directly into PyTorch via eager mode dispatch (RMSNorm, TopK), TorchInductor autotuning (dense, grouped, and MXFP GEMMs), and AOTriton 0.14b+ (SDPA).
- Achieved operator geometric-mean speedups over ATen/Triton baselines of 1.10x for BF16 dense GEMM, 1.58x for MXFP8, 1.68x for MXFP4, 1.20x for grouped GEMM, and up to 4.82x for small-K TopK.
- Delivered end-to-end vLLM whole-request speedups up to 1.13x in BF16, 2.04x in MXFP8, and 3.01x in MXFP4 depending on model and concurrency.

**Why it matters:** It enables PyTorch users on AMD ROCm hardware to achieve significant performance improvements for core LLM primitives without modifying application code or calling custom kernels.

### [Day-0 Support for Flint on vLLM](https://vllm.ai/blog/2026-10-21-flint)

**vLLM Blog** · 2026-10-21

vLLM announced day-0 support for Recursive's 40B-parameter Flint MoE model, achieving ~500 tokens/s decode speed for single requests on an NVIDIA GB200 GPU.

- Flint uses a 49-layer pre-norm MoE architecture with a 2.5B active parameter count per token, sliding-window attention, and a 262K-token context window.
- vLLM supports both NVFP4 (W4A16 weight-only GGUF format repacked at load time) and BF16 checkpoints on a single GPU.
- Custom low-latency kernels reduced the decode step from 1,096 stock kernels down to seven fused kernels per MoE layer for batch sizes up to 8.
- Optimizations improved NVFP4 decode step latency from 4.81 ms to 1.78 ms (2.7x speedup) and reduced an 8,192-token prefill from 207 ms to 145 ms.
- Kernel launches utilize programmatic dependent launch to overlap weight loading with preceding kernel execution.

**Why it matters:** The custom kernel optimizations allow high-throughput, real-time inference of a long-context 40B MoE model on a single GPU setup.

### [The Thin Orchestrator: How We Made Our AI Agents More Reliable by Giving the Router Less to Do](https://engineering.fb.com/2026/10/19/ml-applications/thin-orchestrator-ai-agent-architecture/)

**Meta Engineering** · 2026-10-19

Meta implemented a thin orchestrator pattern, using a 1,300-line deterministic router to handle 20+ workflows across 14 context-isolated subagents for recommendation data column onboarding.

- Replaced a single context-heavy agent with a 1,300-line router that performs zero domain work, code generation, or reasoning.
- Decoupled column onboarding across three codebases and three languages into 14 specialized subagents focusing on isolated domains like schema management, code generation for 10 data sources, and validation.
- Eliminated cross-contamination of subsystem concepts and prevented performance drops seen when single agents relied on manual prompt engineering (which had dropped to 10-20% success without handholding).
- Establishes a fixed 7-step protocol for the orchestrator to check instructions, prevent duplicate targets, gather user fields, and auto-discover repository metadata.

**Why it matters:** Isolating domain context into specialized subagents managed by a lightweight router prevents context interference, improving agent reliability and reducing manual prompt engineering overhead in complex production pipelines.

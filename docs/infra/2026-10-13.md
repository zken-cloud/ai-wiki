### [Extending Inductor for the IBM Spyre Accelerator](https://pytorch.org/blog/extending-inductor-for-the-ibm-spyre-accelerator/)

**PyTorch Blog** · 2026-10-13

IBM migrated the torch.compile backend for its 75W Spyre AI inference accelerator from a custom-built stack to an out-of-tree PyTorch Inductor extension, reducing compiler codebase size by approximately 7x.

- Spyre uses a 32-core dataflow architecture linked by a ring topology, featuring 2 MB per-core scratchpads (64 MB total) and fixed 128-byte data movements termed 'sticks'.
- The torch-spyre backend operates in two stages: Inductor lowers PyTorch FX graphs into SuperDSC IR, which is then translated to native hardware instructions via IBM's DeepTools compiler.
- Hardware-specific lowerings, operation decompositions (e.g., LayerNorm), tiling, layout assignments, and scratchpad memory allocations are injected into Inductor via CustomPreSchedulingPasses.

**Why it matters:** It demonstrates that PyTorch Inductor can be extended to target unconventional, non-GPU hardware architectures like dataflow processors without maintaining a separate standalone compiler.

### [Run multi-node inference workloads using Ray LLM Deep Learning Containers](https://aws.amazon.com/blogs/machine-learning/run-multi-node-inference-workloads-using-ray-llm-deep-learning-containers/)

**AWS Machine Learning Blog** · 2026-10-12

AWS has introduced multi-node Ray LLM Deep Learning Containers (DLCs) to run disaggregated prefill and decode inference across multiple GPU nodes on Amazon EKS.

- The multi-node Ray LLM DLC integrates Ray Serve LLM, NVIDIA Inference Transfer Library (NIXL), and the Elastic Fabric Adapter (EFA) stack to expose an OpenAI-compatible API.
- Prefill and decode phases are disaggregated across separate GPU nodes to eliminate resource contention between compute-bound prefill and memory-bandwidth-bound decode tasks.
- The pre-built container bundles the GPU stack, CUDA libraries, and framework dependencies to eliminate manual assembly and testing of the inference dependency chain.
- This architecture allows independent hardware selection and scaling for prefill and decode nodes, requiring high-speed interconnects for fast KV cache transfers.

**Why it matters:** It eliminates the manual effort of building complex multi-node GPU dependency chains while optimizing inference performance for long-prompt workloads like RAG and document summarization.

### [Turning Opportunistic AI Inference Capacity Into Better Ads Recommendations](https://engineering.fb.com/2026/10/12/ml-applications/turning-opportunistic-ai-inference-capacity-into-better-ads-recommendations/)

**Meta Engineering** · 2026-10-12

Meta developed a system to harvest idle, fragmented inference capacity across its heterogeneous fleet to run opportunistic ads recommendation workloads without increasing baseline hardware orders.

- Opportunistic capacity arises from peak-provisioning gaps, supply chain delivery mismatches, regional resource-ratio mismatches, and accelerator-type non-portability.
- The system uses two elasticity levers: Rank More Ads (RMA) to dynamically scale evaluated candidate volume, and Serve Better Models (SBM) to route request shares to larger models.
- Physical and logical isolation protects reserved baseline capacity, while separate control feedback loops manage RMA candidate volume and SBM coverage.
- Value-aware load shedding at both client and server layers allows optional workloads to degrade gracefully when opportunistic capacity is suddenly reclaimed.

**Why it matters:** It enables large-scale AI infrastructure to maximize hardware utilization and improve recommendation performance without impacting latency targets or purchasing additional accelerator capacity.

### [Improve TTFT for Multi-Turn Agentic Workloads with Bi-Directional KV Transfer in vLLM](https://vllm.ai/blog/2026-10-12-bidirectional-kvxfer-multiturn-agentic-workload)

**vLLM Blog** · 2026-10-12

vLLM added bi-directional KV transfer support, allowing prefill nodes to retrieve previously generated KV cache from decode nodes across multi-turn agentic workloads to eliminate redundant prefill recomputation.

- Conventional prefill-decode disaggregation only transfers KV cache from prefill to decode nodes, forcing prefill nodes to recompute KV projections for generated response tokens on subsequent turns.
- Bi-directional KV transfer lets decode nodes return previously computed KV blocks back to prefill nodes on later turns, preserving context across extended interaction histories.
- In multi-turn benchmarks on Amazon EC2 P5en instances with AWS Elastic Fabric Adapter (EFA), the feature reduced TTFT by up to 1.6x for Qwen3-32B and up to 3.3x for zai-org/GLM-5-FP8.
- The architecture includes NIXL KV connector enhancements, a KV-cache-aware router, block retention TTL controls, and a KV recompute threshold.
- Originally built and validated on AWS Trainium instance clusters, the feature was contributed to vLLM as an accelerator-agnostic capability.

**Why it matters:** It significantly reduces time to first token (TTFT) and improves GPU/accelerator utilization for long multi-turn agentic and conversational workflows.

### [Deploy decision models with llama.cpp on Amazon SageMaker AI](https://aws.amazon.com/blogs/machine-learning/deploy-decision-models-with-llama-cpp-on-amazon-sagemaker-ai/)

**AWS Machine Learning Blog** · 2026-10-12

AWS announced a managed deployment path on Amazon SageMaker AI for running quantized llama.cpp models on CPU or GPU using AWS Deep Learning Containers and the SemIf adapter.

- Uses the AWS Deep Learning Container (DLC) for llama.cpp, which automatically maps POST /invocations to llama-server at /v1/chat/completions for GGUF model files.
- Extends the runtime via a custom child image containing the SemIf adapter (formerly OpenJev) to extract final-position logits and state operations.
- Replaces text decoding in structured decision paths by returning calculated probabilities and option_logits over request-defined option IDs.
- Supports deployment options across both CPU and CUDA/GPU infrastructure.

**Why it matters:** This approach eliminates the need to parse prose output by providing calibrated, fixed-option probabilities directly for application workflows such as agent action selection and support routing.

**AWS Machine Learning Blog** · 2026-10-12

AWS has enabled Amazon Bedrock global cross-Region inference for OpenAI GPT-6 Sol, GPT-6 Luna, and GPT-6 Astra across select Asia-Pacific Regions.

- GPT-6 Sol and GPT-6 Luna global profiles are available from source Regions ap-southeast-1, ap-southeast-3, ap-southeast-5, ap-southeast-7, and ap-east-2; GPT-6 Astra is available from ap-southeast-1.

- Inference is invoked by passing global profile IDs (e.g., global.openai.gpt-6-sol) to the bedrock-runtime endpoint via the Converse API or OpenAI-compatible APIs.

**Why it matters:** Developers in Southeast Asia and Taiwan can scale high-volume GPT-6 workloads beyond local single-Region capacity limits without manually managing multi-Region infrastructure.
